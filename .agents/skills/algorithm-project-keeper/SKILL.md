# Algorithm Project Keeper

让这个推荐算法项目始终简单、真实、可复现、可比较。长期维护两个事实源：仓库根目录的 `PROJECT_STATUS.md` 和 `results/kaggle_log.csv`。代码、Notebook、运行结果和 Git 历史用来核实它们，不另建常驻跟踪表、周报或汇报文档。

## 先核实项目

- 首次使用或项目有明显变化时，按需查看 README、状态文件、实验日志、相关代码或 Notebook、数据字段说明和最近 Git 变更。只读与当前问题有关的部分。
- 分清真实业务数据、Kaggle 代理数据、本地验证、Kaggle 公榜和上线效果。不要将一种结果称作另一种结果。
- 项目目标、输入、输出、负责范围与明确排除范围以已确认资料为准；证据不足写 `待确认`，不扩张范围。

## 维护项目状态

用户要求“更新项目”“目前做到哪里”“当前算法如何实现”等时，核实最近代码和实验，只修改 `PROJECT_STATUS.md` 中发生变化的部分。保持以下简短结构：

1. 项目边界：目标、当前输入、当前输出、负责范围、不负责范围。
2. 当前算法实现：数据集；正负样本；实际入模的用户、活动和交叉特征；模型；分数如何变成 Top-K。
3. 当前实验结果：一个表列版本、模型、主要变化、本地指标、Kaggle Public Score、备注。
4. 当前结论：最多 3–5 条，必须有代码或实验依据。
5. 下一步：最多 3 条可验证的动作。

没有跑出的成绩写 `Pending`，不要推算。只有明显的算法变化才升级版本，说明改了什么、为何修改、结果如何；版本不明时写 `待确认`。

## 记录 Kaggle 实验

`results/kaggle_log.csv` 使用列 `run_id,date,version,model,main_change,local_metric,public_score,notes`。每次真实提交单独追加一行，成功与失败都保留，不覆盖历史；先检查是否已有相同提交。新增公榜分数时，结合用户信息、当前实现和最近变更确定版本与主要变化，生成下一个唯一 `run_id`。无法确定的字段写 `unknown` 或 `待确认`，仍记录已知事实。

记录后更新状态文件中的实验表、当前最佳和相关结论。比较公榜分数只与公榜分数比较；本地 MAP@10 单独标明。回复保持简短，给出新 Run、分数、历史最佳及差值；除非用户要求，不写长篇实验分析。

## 选择与比较算法

先说明当前 Baseline 的具体瓶颈、新方法解决的问题、现有数据是否适合、是否有成熟实现，以及能否公平比较。用户 × 活动或卡券的表格任务可先考虑 LightGBM、XGBoost、CatBoost；排序学习和深度模型取决于数据与树模型的实验瓶颈。不因模型流行而增加召回、粗排、精排等阶段。

比较时尽量固定数据、时间划分、正负样本、特征及主指标，一次只改变一个关键因素。若当前主本地指标是 MAP@10，沿用它；Kaggle Public Score 另列。推荐下一步时给出可执行的验证方式，不把猜测写成既有结论。

## 按需生成领导汇报

只有用户明确要求领导、阶段、周会汇报或 PPT 时才生成。优先读取 `PROJECT_STATUS.md` 和 `results/kaggle_log.csv`，必要时回查代码。汇报简短回答：解决什么问题、做到哪一步、算法流程、已验证效果、最多三个问题与最多三个下一步。清楚标明本地指标与公榜指标，缺失值写待验证。不自动维护 `LEADERSHIP_BRIEF.md`。如果当前环境已有适用的 Operating Review 或 Business Review Skill，可按需使用它转换呈现形式；本 Skill 仍负责事实核对。
